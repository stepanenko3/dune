# Ігрові дані з файлів гри: драйвери джерел і індикатор оновлень

Дата: 2026-10-21. Статус: на погодженні (рецензію будівельником пройдено; рішення користувача: картинки — запасне джерело, невипущене — ховаємо).
Спайк і сирі факти: `~/Library/Application Support/Claude/side-session-notes/local_42e4b3b4-…/game-data-spike.md`, огляд поточних джерел — `current-data-sources.md` там само.

## 1. Навіщо

Зараз усі ігрові дані сайту — чужі: мапи, точки й розкладки Глибокої пустелі (ГП) з TH.GL, предмети/рецепти з questlog.gg, будівлі й ціни будівництва з awakening.wiki, переклади з gaming.tools (імпорт руками в браузері, бо Cloudflare блокує сервер), великі поля меланжу — разова копія Red-Blink. Будь-яке з цих джерел може зникнути, змінити формат або закритися, і сайт тихо застаріє.

Користувач хоче:
- брати все напряму з файлів гри Dune: Awakening (офіційний dedicated server, анонімно зі Steam);
- бачити на сайті, **коли і що** змінилося — і щоб індикатор рухався лише від **реальних** змін;
- механізм, що переживе втрату доступу до файлів гри: інше джерело = ще один драйвер із **тим самим інтерфейсом**, і все працює далі.

Спайк довів, що з серверних файлів доступні: предмети, рецепти, будівлі та ціни, навички (перевірити), переклади на всі 14 мов сайту, ігрові конфіги (ліміти полів меланжу, шторм), розкладки ГП, розміщення ресурсів (`ResourceNodeData`), спавнери полів меланжу. **Картинок немає** (серверний кук вирізав пікселі з усіх текстур).

## 2. Цілі, не-цілі, анти-цілі

**Цілі**
1. Єдиний інтерфейс джерела даних (драйвер) і реєстр, який для кожного розділу даних бере найкраще доступне джерело.
2. Драйвер «файли гри» — основний для всіх розділів, крім картинок.
3. Драйвер «спільнота» (TH.GL + questlog + вікі + gaming.tools) — той самий інтерфейс, запасний; для картинок (іконки, тайли мапи, спрайт значків) — **єдиний** на цьому етапі (рішення користувача).
4. Нормалізовані дані з версією й хешем кожного розділу; оновлення фіксує зміну, лише коли змінився хеш.
5. Індикатор на сайті: коли і що оновлено, по розділах, з джерелом.
6. Працює на Маці (локальна копія), на Linux-сервері сайту і з окремим сервером гри (видобування на одній машині, сайт — на іншій).

**Не-цілі (зараз)**
- Картинки з клієнта гри (Steam-акаунт користувача) — можливий майбутній драйвер, не в цій роботі.
- Живий стан світу (які поля меланжу активні зараз) — з файлів гри його не взяти; позначки гравців (`spice_marks`) лишаються як є.
- Публікація сирих файлів гри, usmap, tar-образів.

**Анти-цілі (провал, навіть якщо «працює»)**
- Зламані збережені дані користувачів: бази, розрахунки калькулятора, бібліотека посилаються на нинішні id (`AluminiumBar`, `AluminiumBarRecipe`, `structures/dune man|foundation`) — вони мусять і далі відкриватися.
- Індикатор, що «оновлюється» щодня без змін (перезбір того самого = не оновлення).
- Невдалий розбір нової збірки гри, що стирає або калічить робочі дані на сайті.
- Залежність сайту в рантаймі від Docker/.NET: важке видобування — окремий інструмент; сайт лише читає готовий нормалізований пакет.
- Поширення файлів гри або картинок із них.

## 3. Обмеження

- Право: EULA DA §7(g) забороняє datamining, крім дозволеного місцевим законом. Користувач свідомо обрав цей шлях; публікуємо лише похідні факти (назви, числа, координати), не файли гри й не асети.
- Сервер сайту без браузера/headless; усе в Node.
- Живий дев-сервер `dune.test` перезапускається від змін у `server/lib`, `server/routes`, `locales` і проганяє стартові міграції на ЖИВІЙ базі `dune`: міграції лише адитивні й ідемпотентні; перевірка — на копії `dune_preview` через окремий порт (`spice-api`/`spice-web` у `.claude/launch.json`); у живу базу без дозволу не писати.
- Тексти інтерфейсу — через `t()` з українськими ключами, 14 мов; нові переклади — у `locales/parts` + `npm run i18n:merge` (ніколи `--clean`).
- Тека не git; паралельно працюють інші сесії — чужих файлів не чіпати.
- Координати: TH.GL x = Y гри, TH.GL y = X гри.
- Стабільність id (див. §6).

### 4.1 Розділи даних (sections)

Кожен розділ має id, версію схеми і нормалізовану форму (JSON). Перелік (рішення будівельника — дробити дрібніше, якщо зручно):

| Розділ | Зміст | Файли гри (джерело) |
|---|---|---|
| `items` | предмети: id, англ. назва, категорія/підкатегорія, тір/грейд, рідкість, стек, об'єм, ключ іконки | `DT_BaseItems_*` |
| `placeables` | розміщувані пристрої: енергія, вода, тощо | `DT_BaseItems_Placeables`, `DT_Buildable*` |
| `recipes` | рецепти: входи/виходи, час, вода, станції | `DT_ItemsCraftingRecipes`, `DT_CraftingProductionTypes` |
| `buildables` | будівельні модулі за сетами: здоров'я, ціна будівництва | `DT_BuildingData_*`, `DT_Buildable*`, `DT_BaseItems_BuildingSets` |
| `skills` | дерево навичок, рівні, вимоги, спеціалізації | `DT_SkillTree*` та суміжні (перевірити на старті фази 2) |
| `texts` | назви/описи для всіх сутностей, 14 мов | `Content/Localization/Game/<lang>/Game.locres`, `ST_Localization_*` |
| `maps` | список мап (Hagga Basin, ГП, інші), межі у світових координатах | рівні + `DefaultGame.ini` |
| `markers` | точки інтересу (печери, табори, аванпости…) | рівні/контент-блоки, `markers`-типи |
| `resources` | розміщення ресурсів (тип, кластер, точки) | `ResourceNodeData` у CB_* рівнях, `BP_*Ore*_Spawner` |
| `spice` | місця полів меланжу малі/середні/великі + ліміти | `BP_SpiceField_*`, `DA_FieldType_Spice_*`, `[SpiceHarvestingSystem]` в ini |
| `ddLayouts` | розкладки ГП: порядок ротації, вміст кожної (кластери → точки) | `[WorldLayoutSubsystem] m_WorldLayoutsPerWorld`, `DA_DeepDesert_1_Layout_*`, `WLC_*` |
| `config` | шторм Коріоліса (тривалості стадій), інше корисне з ini | `DefaultGame.ini` |
| `images` | іконки, тайли мап, спрайт значків | **лише драйвер «спільнота»** |

Нормалізована форма кожного розділу — незалежна від джерела: англ. назви + ключі текстів; координати в пакеті — світові одиниці гри, драйвер віддає їх сайту в нинішньому кадрі мапи (див. §4.6); посилання між розділами — за стабільними id.

### 4.2 Інтерфейс драйвера (JS, сайт)

```js
/** @typedef {'items'|'placeables'|'recipes'|'buildables'|'skills'|'texts'|'maps'|'markers'|'resources'|'spice'|'ddLayouts'|'config'|'images'} Section */
class GameDataDriver {
  id            // 'gamefiles' | 'community' | …
  label         // для індикатора: «файли гри», «запасне джерело»
  /** які розділи вміє давати (може залежати від стану: нема пакета → []) */
  sections(): Section[]
  /** дешева перевірка: чи з'явилось щось нове (build/manifest/etag), без повного збору */
  async probe(): Promise<{ version: string, build?: string, at?: string }>
  /** нормалізовані дані розділу + версія джерела */
  async load(section: Section, opts?: { lang?: string }): Promise<{ data: any, version: string }>
  /** для images: віддати байти картинки за нормалізованим ключем (іконка, тайл) */
  async asset?(kind: 'icon'|'tile'|'sprite', key: string): Promise<{ body: Buffer|Stream, type: string } | null>
}
```

- Реєстр: упорядкований список драйверів за пріоритетом (`gamefiles` → `community`), налаштовується в адмінці. Для кожного розділу береться перший, хто його дає й успішно віддає дані; збій — переходимо до наступного, і це видно в індикаторі.
- Новий драйвер (клієнт гри, чужий API, ручний пакет) = новий клас із цим інтерфейсом + рядок у реєстрі. Нічого більше не змінюється.
- Хеш розділу рахує реєстр (не драйвер): стабільна серіалізація нормалізованих даних (відсортовані ключі/масиви за id) → sha256. Однакові дані з різних драйверів дають однаковий хеш.

### 4.3 Пакет (bundle) від видобувача

Тека (або архів) з:
- `manifest.json`: `{ schema, game: { build: "2160922", version: "1.5.15", manifestId, depot }, extractedAt, extractor: { version }, sections: { <id>: { file, schema, hash, count } } }`;
- `sections/<id>.json.gz` — нормалізовані дані (ті самі форми, що й у §4.1).

Сирих файлів гри в пакеті нема. Драйвер `gamefiles` читає найсвіжіший валідний пакет: з локальної теки (`GAMEDATA_BUNDLE_DIR`) або прийнятий через `POST /api/admin/gamedata/bundle` (токен у налаштуваннях; для окремого сервера гри). Пакет перевіряється (схема, хеші, мінімальні обсяги) до того, як стане «поточним».

### 4.4 Видобувач (`dune/tools/game-extractor/`)

- **.NET-консоль на CUE4Parse** (закріплена версія; Dune-специфіка вже є в бібліотеці; Oodle — керований OodleSharp, тож працює і на arm64). Отримує паки, usmap, список потрібних ассетів → сирі JSON + `.locres` + `.ini`.
- **Нормалізатор**: правило будівельника, де саме нормалізувати (у .NET чи в Node-скрипті поряд). Він має бути покритий тестами на зразках.
- **Обгортка-скрипт** з кроками `check | fetch | usmap | extract | normalize | deliver | all`, ідемпотентна; кожен крок кешує результат за build (той самий build → usmap і сирі файли не перераховуються).
- **Завантаження**: DepotDownloader (SteamCMD падає під емуляцією на Mac arm64), анонімно, app 4754530, Linux-депо. `check` порівнює manifest id без завантаження.
- **usmap**: метод зі спайку — завантажити образ у Docker, запустити бінарник без мережі й БД (`--network none`), дочекатися «Game Engine Initialized», `SIGSTOP`, знайти `FNamePool`/`GUObjectArray` сканером пам'яті, `jmap_dumper` у ручному режимі (з нашим патчем розкладки `UClass` для Dune: +0x18 після `NetFields`), конвертувати в `.usmap`. Патч jmap і сканер — у репозиторії видобувача. Потрібні `linux/amd64` (на Маці — емуляція Rosetta, працює).
- **Упаковка**: Docker-образ(и) видобувача; один і той самий запуск на Маці, Linux-сервері сайту і окремому сервері гри. Хост видобування потребує Docker і ~15 GB місця.
- **Розклад**: на хості видобування — cron (або існуючий cron сайту, якщо видобувач на тій самій машині) кожні N годин робить `check`; нова збірка → `all`.

### 4.5 Стійкість до збоїв нової збірки

Патч гри може зламати розбір (нова розкладка UClass, нові поля, зміна форматів). Правила:
- Невдалий крок → пакет не створюється; на сайті лишаються попередні дані; індикатор показує «гра оновилась до X, дані ще від Y» і причину для адміна.
- Запобіжник обсягу (як нинішній `SWEEP_MIN`): розділ, що раптом зменшився більш ніж удвічі, не застосовується автоматично — чекає підтвердження адміна.
- Кожен розділ застосовується незалежно: зламаний `resources` не блокує оновлення `items`.
- Якщо файли гри стануть недоступні зовсім — драйвер `gamefiles` просто не дає розділів, реєстр бере `community` (або останні збережені дані, якщо й воно недоступне).

### 4.6 Координати *(рішення автора дизайну)*

- **Кадр зберігання й API не змінюється**: збережені дані (`spice_marks.x/y`, `data/large-spice.json`, `dd-history.json`, налаштування мапи) і відповіді `/api/map/*` лишаються в нинішньому кадрі (координати TH.GL; номери розкладок = сід Коріоліса 0–11 як зараз). Жодної міграції збережених рядків.
- Драйвер `gamefiles` перетворює світові одиниці UE (X, Y, Z) у цей кадр (TH.GL x = Y гри, TH.GL y = X гри; масштаб/зсув — з `transformation` TH.GL), перевірено тестом на відомих точках (сітка секторів, кілька печер/аванпостів, що збігаються в обох джерелах).
- Номер розкладки: драйвер `gamefiles` дає відповідність «сід → асет `DA_DeepDesert_1_Layout_NN`», яку підтверджує звірка вмісту з тим, що TH.GL показує для того самого сіду; поки не підтверджено — драйвер не віддає `ddLayouts`/точки ГП для такого сіду (беремо `community`), щоб позначки гравців не опинились на чужій розкладці.
- Розміщення в контент-блоках — відносні: нормалізатор складає трансформи (TerrainBlock/кластер ГП → CB → вкладені CB → точка) у світові, далі — перетворення в кадр сайту.

### 4.7 Розкладки ГП

- Порядок ротації — з `m_WorldLayoutsPerWorld` (індекс → `DA_DeepDesert_1_Layout_NN`; зараз 0–14, 15 = QA-кластери, 16 = Layout_16, 17 = Layout_18; у 12+ немає шару мапи). Розкладки без шару мапи показуємо, якщо є дані, але позначаємо.
- Яка розкладка активна — як і зараз, за сідом Коріоліса (+1 щотижня, зараз 11) з `storm.mjs`; `dd-history` продовжує вести спостереження. Зв'язок «сід → індекс у списку» лишається припущенням, яке можна звірити зі спостереженнями (поле в індикаторі «розкладка за розрахунком / підтверджена»).

### 4.8 Переклади

- `texts` з `Game.locres` (14 мов) — основне джерело назв і описів. Відповідність мов: `zh-Hans`↔`zh-CN`, `zh-Hant`↔`zh-TW`, `pt-BR`↔`pt-BR`, решта 1:1.
- У `game_texts.source` з'являється `game`. Пріоритет: `manual` (locked) > `game` > `gamingtools` > `thgl`. Ручні правки ніколи не затираються.
- Підписи мапи й луту теж беруться з `texts`, а не з dicts TH.GL, коли розділ доступний із файлів гри.
- Імпорт із gaming.tools у браузері лишається як запасний інструмент адміна.

## 5. Індикатор оновлень

**Дані**
- `gamedata_sections(section PK, driver, version, hash, count, schema, applied_at, checked_at, status, error)` — поточний стан кожного розділу.
- `gamedata_changes(id, at, section, driver, game_build, from_hash, to_hash, summary JSON)` — журнал; рядок з'являється **лише** коли змінився хеш. `summary`: додано/прибрано/змінено (кількості) + до ~20 прикладів назв (id + англ. назва; мовою відображення — через `texts`).
- `gamedata_builds(build, manifest_id, seen_at, extracted_at, status)` — які збірки гри бачили й чи розібрали.
- Міграції лише адитивні.

**Що бачить відвідувач** (рішення будівельника в деталях, у межах правил макету з пам'яті: мобільна ширина, без обрізання, хлібні крихти)
- Компактний значок у футері (або шапці «Ще»): «Дані гри: версія 1.5.15 · оновлено 19 жов» — веде на сторінку.
- Сторінка «Оновлення даних»: зверху — версія гри й дата останньої реальної зміни; таблиця розділів (назва, джерело — «файли гри» / «запасне джерело», коли востаннє змінився, скільки записів); нижче — стрічка змін по датах: «Предмети: +12, −3, змінено 40 (приклади…)».
- На сторінках, що показують дані (Каталог, Калькулятор, Мапа, Навички), — дрібний підпис «оновлено …» відповідного розділу з посиланням на стрічку.

**Для адміна**: стан драйверів, остання перевірка Steam, помилки видобування, розділи на підтвердженні (запобіжник обсягу), кнопки «перевірити зараз», «застосувати», «повернути попередню версію розділу», налаштування пріоритету драйверів.

## 6. Стабільність id

- Предмети, розміщувані й рецепти вже мають ігрові id (імена рядків DataTable: `AluminiumBar`, `AluminiumBarRecipe`) — лишаються як є.
- Будівлі зараз мають ключі вікі (`structures/dune man|foundation`), на які посилаються збережені розрахунки. Потрібна таблиця відповідності «старий ключ → ігровий id», зіставлена автоматично (іконки вікі мають ігрові імена текстур, напр. `T_UI_IconPlacNeutDesertMechanicFoundation_D`; плюс назва/сет), неоднозначні — на ручне зіставлення в адмінці. Публічний ключ для старих записів не змінюється; нові записи отримують ігровий id.
- Типи точок мапи: TH.GL-id (`cave`, `enemycamp`…) зіставляються з ігровими типами маркерів; збережені налаштування шарів користувачів мусять працювати далі.
- Навички *(рішення автора дизайну)*: id зараз — slug-и questlog (`skills_ability_assaultseeker`), а короткий код білду `?b=` (`encodeShort`, `src/lib/skills.ts`) кодує ранги за позицією. Старі посилання мусять розкодовуватись точно: заморожена таблиця «старий slug/позиція → ігровий id» і версія в коді білду (новий формат для нових посилань, старий декодується через таблицю). Якщо в даних гри немає позицій дерева (x/y) — розкладка дерева лишається з `community`.
- Рядки, закріплені вручну (`locked`) у `game_*`: імпорт їх не чіпає (як зараз); в адмінці — позначка, де дані гри тепер відрізняються.
- Іконки: ключ іконки — ігровий шлях ассета (`/Game/Dune/GUI/Textures/Icons/…/T_UI_…_D`); драйвер `community` віддає за ним картинку з questlog CDN (там ті самі шляхи), як і зараз через `/catalog-icons/`.

## 6a. Невипущений контент *(рішення користувача)*

У серверних файлах є тестове, вирізане й ще не випущене (QA-кластери, `Prototyping/`, `[DEPRECATED]`, предмети без перекладу тощо). **Ховаємо**: на сайті й у публічній стрічці змін — лише те, що є в грі. Адмін може відкрити окремий запис вручну.

- Нормалізатор позначає кожен запис `released: true/false` з причиною (`reason`), не викидаючи його з пакета: правило будівельника, орієнтири — є справжня назва в `Game.locres` (не заглушка), шлях не в тестових/редакторських теках, не позначено застарілим, запис досяжний (рецепт, продавець, лут, будівельний сет, розміщення на мапі).
- Невипущене не потрапляє у видачу сайту, у підрахунки індикатора й у публічну стрічку змін; у журналі змін для адміна видно окремо («з'явилось у файлах, ще не в грі»).
- Ручне відкриття — прапорець адміна на записі (поруч із нинішніми `hidden`/`locked`), переживає наступні оновлення; коли запис стає `released` сам, прапорець більше не потрібен.
- Запобіжник обсягу рахує лише випущене.

## 7. Етапи (порядок поставки)

1. **Каркас без зміни поведінки**: інтерфейс, реєстр, таблиці стану/журналу, драйвер `community` як обгортка нинішнього коду, індикатор і сторінка (показує поточне джерело — запасне). Нічого не ламається, індикатор уже чесний.
2. **Видобувач + `gamefiles` для `items`, `placeables`, `recipes`, `buildables`, `texts`, `config`** (+ таблиця відповідності будівель). Звірка з нинішніми даними (diff-звіт) перед перемиканням пріоритету.
   *(рішення автора дизайну)* Каталог після перемикання виглядає так само: ті самі фільтри, категорії, URL. Нормалізатор перекладає ігрові категорії/грейди в нинішню таксономію сайту таблицями відповідності; регрес видимого (зниклий фільтр, порожня категорія, сирий id замість назви) = помилка. Пріоритет розділу перемикає адмін кнопкою після перегляду diff-звіту в адмінці (по розділу, з відкатом).
3. **`skills`**.
4. **Мапа: `maps`, `markers`, `resources`, `spice`, `ddLayouts`** — складання трансформів, координати, звірка з TH.GL на відомих точках; `data/large-spice.json` замінюється даними гри.
5. **Автоматизація**: розклад перевірки Steam, push з окремого хоста, адмін-керування; `community` лишається лише запасним (і для картинок).

## 8. Перевірка

- Тести нормалізатора на зразках (обрізаних JSON із спайку — похідних, не файлів гри).
- Тести реєстру: пріоритет/відкат на запасний драйвер; хеш стабільний до порядку; журнал не пишеться без зміни хешу; запобіжник обсягу.
- Інтеграційно — на копії `dune_preview`: застосувати пакет, переконатися, що каталог/калькулятор/бази/мапа відкриваються, старі розрахунки знаходять будівлі.
- Видобувач: прогін `all` на Маці; на Linux — той самий образ (перевірити до кінця етапу 5).

## 9. Залишено будівельнику

Точні нормалізовані схеми полів кожного розділу; формат стабільної серіалізації; де саме живе нормалізація; вибір конкретних DataTable для кожного поля (за спайком і порівнянням з нинішнім каталогом); дизайн значка й сторінки в межах правил макету; розклад перевірок; формат токена для push; структура Docker-образів.

## 10. Відомі ризики й припущення

- Автоматичний usmap залежить від того, що бінарник стартує під Docker (на Маці — Rosetta) і що патч гри не змінить розкладку `UClass`/`FNamePool`. Якщо зміниться — видобування зупиняється чесно (§4.5), правиться сканер/патч.
- «Сід Коріоліса → індекс розкладки» — припущення.
- Частина даних, що зараз з вікі (здоров'я будівель), може бути не в DataTable прямо, а в класах/CDO — тоді або через jmap/CDO, або лишається з `community`.
- Linux-сервер і окремий сервер гри: передбачено, що там є Docker.
